# YanXing v0.1.2

2026-09-09

研行 0.1.2 将 Docker 部署从多容器改为**单一 `app` 容器**，并完善 supervisor 生命周期、联合健康检查、测试隔离与升级文档。这是**部署方式的破坏性变化**：已发布的 `v0.1.1` 仍是 Web / Worker / migrate 多容器布局，不能与本版本 `compose.yaml` 混用。

## 主要更新

### 单一 `app` 容器

- Compose **只有一个 `app` 服务**。默认入口启动 supervisor：先执行数据库迁移，再同时管理 Web 与 Worker。
- **不再保留** `web` / `worker` / `migrate` 服务，也不提供 `all` 启动模式。不要把 `v0.1.1` 镜像配到新 Compose 上，也不要把新镜像配到旧 Compose 上。
- 管理命令仍通过入口脚本提供：`migrate`、`user:create`、`storage:reconcile`、`storage:relocate`。创建管理员所需的密码传入方式见下文。
- 不使用 Compose 时，`docker run` 必须加 `--init`，以便 PID 1 回收 Web / Worker 子进程。

### 生命周期与健康检查

- Web 或 Worker **任一退出**（即使退出码为 0）时，supervisor 会停止另一方并以非零状态退出，由 Docker 按 `restart: unless-stopped` **重启整个容器**。supervisor 不会在容器内单独拉起某一个子进程。
- 联合健康检查要求 Web `/api/health` 与 Worker 心跳都通过。容器被标记为 `unhealthy` **不会**因此自动 restart；需要对 `unhealthy` 做监控告警后诊断。
- 默认共享资源：内存 `YANXING_MEMORY=4g`、CPU `YANXING_CPUS=4`、`pids_limit=512`。supervisor 内部宽限约 80 秒，Compose 停机宽限为 100 秒；直接运行容器时须设置 `--stop-timeout 100`，或使用 `docker stop -t 100`。合并不节省内存，不要把上限降到约 2g，也不要扩容容器。

### 测试隔离与异常清理

- 健康测试显式隔离工作目录、数据库和知识库路径，直接运行测试文件也不会让 Worker 存储维护扫描项目资料。
- 生命周期测试统一登记 supervisor、嵌套 runner 与执行 Promise；回调异常后先请求停止并有界等待，再收集后代、强制清理和回收句柄，保留原始测试错误。
- 增加启动早期失败、未手动登记 PID、嵌套 runner 失败及忽略 TERM 等清理回归。

### 管理员创建示例

文档中的管理员创建步骤保留隐藏输入、导出与清除密码变量，避免把密码写入 shell 历史或长期写入 `.env`：

```bash
read -rsp "管理员密码: " YANXING_ADMIN_PASSWORD; echo
export YANXING_ADMIN_PASSWORD
docker compose exec -e YANXING_ADMIN_PASSWORD app /app/scripts/docker-entrypoint.sh user:create
unset YANXING_ADMIN_PASSWORD
```

## 升级说明

本次**没有**数据库 schema、数据卷布局或密钥格式变更。升级仍须先备份，并保留用于回滚的旧镜像。

从 `v0.1.1` 及更早的多容器部署升级是破坏性部署变化：

1. **先不要**用新 `compose.yaml` 直接 `up` 到仍在运行的旧项目。
2. 用**旧 Compose**（`web` / `worker` / `migrate`）执行 `stop`、完整备份，再 `docker compose down`（**不要加 `-v`**）。保持同一项目名、同一数据卷和原 `YANXING_SETTINGS_ENCRYPTION_KEY`。
3. 若当前目录已是新代码，可用 `git show v0.1.1:compose.yaml` 抽出旧文件，并加 `--project-directory "$PWD"` 与原项目名。
4. 旧的 `YANXING_WEB_MEMORY` / `YANXING_WORKER_MEMORY` 及对应 CPU 限制不再生效，改为共享的 `YANXING_MEMORY` / `YANXING_CPUS`。
5. 将 `YANXING_IMAGE` 改为**新标签**，不要覆盖用于回滚的 `v0.1.1` 或旧本地标签：
   - 发布前、流水线进行中，或 Packages 尚未确认 `v0.1.2` 时：本地构建（例如 `yanxing:v0.1.2-local`），`docker compose up -d --build --wait --wait-timeout 180`。
   - 仅当 `v0.1.2` Release 的 CI、Docker 部署冒烟与镜像发布全部成功，且 GitHub Packages 上该标签可用之后：设为 `ghcr.io/anacondakc/yanxing:v0.1.2`，再 `docker compose pull` 与 `docker compose up -d --no-build --wait --wait-timeout 180`。
6. 生产环境必须使用 HTTPS。不要假定 `latest` 已经是单容器布局。

详细步骤见 [Docker 部署指南](https://github.com/AnacondaKC/YanXing/blob/v0.1.2/docs/docker-deployment.md)。

## Docker 镜像

GitHub Release **发布（`published`）之后**才会启动镜像工作流。须等待对应 Actions 的 **CI、Docker 部署冒烟与镜像推送全部成功**，并在 Packages 上确认 `v0.1.2` 标签可用后，再执行 pull。工作流成功前，该镜像标签可能尚不可用。 发布前或流水线进行中，本地构建仍然可用。

- 镜像：`ghcr.io/anacondakc/yanxing:v0.1.2`
- 平台：仅 `linux/amd64`
- 仅当该 Release **未**标记为预发布且发布成功时，才会更新 `latest`。`latest` 表示最近一次成功的稳定版发布，不是 semver 最大值；在确认成功之前，不要假定 `latest` 已经是单容器布局。生产部署应固定 `v0.1.2` 标签。
- 预构建镜像上传上限为 `26214400` 字节，运行时须保持一致；自定义上限需自行构建。GHCR 包若为私有需先登录。

在确认 Packages 标签可用后，于 `.env` 中设置 `YANXING_IMAGE=ghcr.io/anacondakc/yanxing:v0.1.2`：

```bash
docker compose config --quiet
docker compose pull
docker compose up -d --no-build --wait --wait-timeout 180
docker compose ps -a
```
