# YanXing v0.2.0

2026-09-13

研行 0.2.0 将工作台切换为**课题 → 阶段 → 不可变报告提交**原生模型，并整理浅色界面、精简内部实现、加固测试与 CI。这是**数据模型的破坏性变化**：已发布的 `v0.1.x` 数据库、schema 备份和 GHCR 镜像都不能直接用于本版本；**不提供历史迁移或双模运行**。

## 主要更新

### 课题、阶段与不可变提交

- 研究进度按有序阶段管理：阶段内可多次完整提交，阶段完结报告与更新报告分开，完结后仍可补交并接替正式成果。
- 报告提交改为准备（解析上传）与确认两步，使用幂等键；网络结果不确定时保留同一提交身份重试，不会悄悄再传一份文件。
- 分析与洞察改为独立的原生任务，由同一镜像内的 Worker 执行；失败、取消不占用成功次数，有资格时可手工重试为新代次。
- 增加同模型原生备份 / 恢复：SQLite 一致性快照、正式/墓碑报告文件、知识资料和加密设置；**主密钥另行保管，不放入归档**。恢复只接受同一 schema、同一绑定路径和同一密钥，不覆盖现有数据。

### 工作台与界面

- 统一浅色工作台：洞察空状态、报告阅读与阶段标签（如「阶段01 · 开题研究」）按课题里程碑展示，时间统一为北京时间。
- 思维导图按画布等比适配，整张导图完整可见；画布尺寸变化时重新适配，手动缩放或拖动后保持用户视图。
- 热力图改为原生 SVG（视觉保持原样），去掉 `@visx/heatmap` 与 `tw-animate-css` 依赖。

### 安全、存储与任务

- 经反向代理部署时，默认不信任 `X-Forwarded-*`；仅当 Web 只能经可信代理访问时开启 `YANXING_TRUST_PROXY`。
- 原生分析 / 洞察必须配置稳定的 `YANXING_SETTINGS_ENCRYPTION_KEY`；共享设置文件里的 `.settings-key` 不能代替 Web / Worker 主密钥。
- 空业务库没有知识引用时，维护任务不会自动删除知识根中的陈旧未知文件。
- 确定的阶段 / 工作流 / 计划冲突可从「结果未确认」收敛为冲突，需重新读取令牌后再确认；真正的网络不确定仍保留原幂等键。

### 测试、CI 与文档

- 测试运行器在隔离工作区中执行，空发现集失败退出；CI 增加固定种子的随机顺序、覆盖率产物和真实浏览器交互。
- 公开文档改为仓库默认 Compose 路径（`.env`、项目名 `yanxing`、卷 `yanxing_data`），并写明已发布的 `v0.1.x` 镜像不是本模型。

## 升级说明

**不要把 `v0.2.0` 镜像或源码指到现有 `v0.1.x` 数据卷，也不要清空旧库绕过启动检查。** 旧库 / 混合库会明确拒绝启动。

1. 保留旧实例及其镜像、数据卷和 `YANXING_SETTINGS_ENCRYPTION_KEY`，按需做旧版备份。旧数据不能导入新系统。
2. 使用本版本源码中的 `compose.yaml`。默认项目名为 `yanxing`、卷为 `yanxing_data`。若宿主机已有同名项目或卷，必须改用 `-p <新项目名>` 并确认产生的是**新卷**。
3. 复制 `.env.example` 为新的 `.env`（已存在时不要覆盖），写入一次性生成的固定 `YANXING_SETTINGS_ENCRYPTION_KEY`，并确认端口与模型渠道。
4. 镜像标签：
   - 发布流水线完成前：本地构建（默认 `yanxing:local`），`docker compose --env-file .env up -d --build --wait --wait-timeout 180`。
   - 仅当本 Release 的 CI、Docker 冒烟、浏览器检查与镜像发布全部成功，且 GitHub Packages 上 `v0.2.0` 可用之后：设置 `YANXING_IMAGE=ghcr.io/anacondakc/yanxing:v0.2.0`，再 `docker compose pull` 与 `up -d --no-build --wait --wait-timeout 180`。
5. 容器健康后创建管理员（会更新同名账号并使已有会话失效，不要每次启动都跑）：

```bash
read -rsp "管理员密码: " YANXING_ADMIN_PASSWORD; echo
export YANXING_ADMIN_PASSWORD
docker compose --env-file .env run --rm -e YANXING_ADMIN_PASSWORD app user:create
unset YANXING_ADMIN_PASSWORD
```

6. 正式登录必须走 HTTPS。经反向代理时，仅当 Web 只能经可信代理访问才开启 `YANXING_TRUST_PROXY`。不要假定 `latest` 在流水线成功前已经是 0.2.0。

详细步骤见 [Docker 部署指南](https://github.com/AnacondaKC/YanXing/blob/v0.2.0/docs/docker-deployment.md)。

## 发布前验证

以下说明**不能**等同于 GitHub Release 后的自动 CI / Docker 冒烟 / 浏览器检查 / 镜像推送已经完成。自动化测试使用模拟模型，**不能**替代真实外部模型兼容性、HTTPS 浏览器登录或备份恢复演练。

- 发布后由 [镜像发布工作流](https://github.com/AnacondaKC/YanXing/blob/v0.2.0/.github/workflows/docker-release.yml) 调用完整 CI（类型检查、测试、随机顺序、覆盖率、真实浏览器、构建与 Docker 部署冒烟），全部通过后再推送 GHCR 镜像。

## Docker 镜像

GitHub Release **发布（`published`）之后**才会启动镜像工作流。须等待对应 Actions 的 **CI、Docker 部署冒烟、浏览器检查与镜像推送全部成功**，并在 Packages 上确认 `v0.2.0` 标签可用后，再执行 pull。工作流成功前，该镜像标签可能尚不可用；期间仍可本地构建。

- 镜像：`ghcr.io/anacondakc/yanxing:v0.2.0`
- 平台：仅 `linux/amd64`
- 仅当该 Release **未**标记为预发布且发布成功时，才会更新 `latest`。`latest` 表示最近一次成功的稳定版发布，不是 semver 最大值。生产部署应固定 `v0.2.0` 标签。
- 预构建镜像上传上限为 `26214400` 字节，运行时须保持一致；自定义上限需自行构建。GHCR 包若为私有需先登录。

在确认 Packages 标签可用后，于 `.env` 中设置 `YANXING_IMAGE=ghcr.io/anacondakc/yanxing:v0.2.0`：

```bash
docker compose --env-file .env config --quiet
docker compose pull
docker compose up -d --no-build --wait --wait-timeout 180
docker compose ps -a
```
