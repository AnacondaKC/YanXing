# YanXing 课题—阶段—报告工程设计报告

> 文档状态：工程设计草案，可进入技术评审；尚未实施。
> 需求依据：本次产品讨论中用户最后确认的规则。较早讨论中“禁止跳阶段”“允许修改报告归属”“全面取消 V1/V2”“所有旧报告都不能分析”等口径已被覆盖，不再作为实施依据。
> 本文区分：**已确认业务规则（BR）**、**建议工程决策（ADR）**、**待确认边界（Q）**。工程建议不等于已获产品确认。
> 范围：YanXing 业务项目，不涉及 DeepSeek Harness GUI。

## 1. 摘要与目标

YanXing 的业务模型确定为：**课题 → 有序研究阶段 → 阶段内多次完整报告提交**。

本次改造不是删除所有版本概念，而是拆开三种原先混用的语义：

| 语义 | 权威依据 | 业务用途 |
| --- | --- | --- |
| 课题研究进度 | 阶段顺序、名称、状态 | 当前阶段、跳阶段、阶段完结、课题完成 |
| 阶段正式成果 | 阶段当前完结报告 | 阶段正式交付、完结后的补交接替 |
| 报告提交先后 | 阶段内版本号、全课题成功提交序列 | 阶段内 V1/V2 展示、全课题最新判断、跨阶段比较 |

目标：

1. 阶段内多次上传不再自动等于多次阶段推进。
2. 每个阶段具有自己的 V1、V2……，全课题仍保留明确的提交先后关系。
3. 完结报告可被新提交接替，但原文件、历史成果与角色变更记录可追溯。
4. 阶段完成不可逆，允许跳阶段与已完成阶段补交。
5. 所有写入口共享权限、阶段状态机和报告分析资格规则。
6. 文件、数据库、Worker 在失败、重试、并发情况下保持一致。

非目标：不增加审批流程，不支持并行进行中的阶段，不支持报告提交后改归属，不支持覆盖原文件来实现正常修订，不将本次改造扩展为通用文档协作或分支合并系统。

## 2. 术语与展示口径

| 术语 | 定义 |
| --- | --- |
| 课题 Project | 研究目标、成员、研究计划的顶层容器 |
| 阶段 Stage | 课题内具有稳定 ID、顺序、名称、排期和状态的研究单元；兼容现有 milestone 术语 |
| 报告 Report | 一次成功提交的完整报告记录，归属于一个确定阶段 |
| 阶段更新报告 Update | 当前不承担该阶段完结成果角色的报告，包含被新完结报告接替的旧完结报告 |
| 阶段完结报告 Completion | 被指定为该阶段当前正式成果的报告，一个阶段最多一份 |
| 阶段内版本 Stage Version | 成功提交时在该阶段内分配的序号，以 V1、V2……展示 |
| 全课题提交序列 Submission Sequence | 成功提交事务内分配的课题级单调序号，用于确定先后；不作为用户可见的全课题版本号 |
| 最新报告 Latest Submission | 课题内未撤回、未删除的成功提交中，提交序列最大的一份 |
| 旧报告 Historical Submission | 同课题内除最新报告以外的其他有效报告，不等于“已完成阶段报告” |
| 比较基准 Comparison Baseline | 当前报告之前、同课题内最近的一份有效成功提交，可跨阶段 |

建议展示：

- 阶段标题：阶段01 · 开题研究。
- 更新报告：开题研究 V2；紧凑位置显示阶段01 V2。
- 当前完结报告：开题研究完结报告，并保留 V3 标识。
- 完结角色与版本身份分开展示；被接替后 V3 不改变，仅角色变为阶段更新。
- 阶段编号至少两位，不限制为两位；阶段序号与版本号不得拼成无法区分的单一数字。
- 报告实际文件名、报告标题仍保留，不被上述系统标签覆盖。

## 3. 已确认业务规则

### 3.1 权限与归属

| 编号 | 规则 |
| --- | --- |
| BR-01 | 只有课题负责人和管理员可以上传报告；编辑、其他成员及只读用户没有上传权限。 |
| BR-02 | 上传前必须选择文件、所属阶段、更新或完结类型，再确认提交。 |
| BR-03 | 文件保存且基础解析成功，才能正式确认报告及阶段变化。AI 分析不属于正式提交的成功条件。 |
| BR-04 | 正式提交后报告所属课题、阶段不可修改。 |
| BR-05 | 完结及完结后的补交由负责人或管理员直接执行，无审核流程。 |

### 3.2 阶段与课题状态

| 编号 | 规则 |
| --- | --- |
| BR-06 | 一个课题不允许多个阶段同时进行中。 |
| BR-07 | 当前阶段提交更新报告，阶段保持进行中。 |
| BR-08 | 当前阶段提交完结报告，阶段完成，下一阶段自动进入进行中。 |
| BR-09 | 可向后续阶段提交；目标阶段之前尚未完成的阶段自动完成，已有报告保留，没有报告也允许完成。 |
| BR-10 | 已完成阶段只能通过新的完结报告进行补交；跳过且无报告的阶段也适用。 |
| BR-11 | 新完结报告接替旧完结报告，旧报告自动成为更新报告，文件及已有分析、洞察保留。 |
| BR-12 | 已完成阶段不能回退为未完成；补交不回退当前研究进度。 |
| BR-13 | 最后阶段完结后课题自动完成；后续补交或更新完结报告不改变课题完成状态。 |

### 3.3 历史、分析与洞察

| 编号 | 规则 |
| --- | --- |
| BR-14 | 普通更新报告可以按权限撤回或删除；当前完结报告不允许直接删除，只能被新完结报告接替。 |
| BR-15 | 每份报告保留自己的分析和洞察，不因新提交而覆盖其他报告成果。 |
| BR-16 | 全课题最近成功提交的有效报告允许手动重新分析；旧报告成功分析过一次后禁止手动重新分析。 |
| BR-17 | 旧报告从未成功分析时允许首次分析、失败重试；已启动的首次分析可继续，不因新报告出现而中断。 |
| BR-18 | 洞察适用相同资格规则；分析与洞察分别判断成功历史。 |
| BR-19 | 提交时为目标阶段首份报告，不展示“较上一份变化”。 |
| BR-20 | 非阶段首份报告与同课题在其之前最近成功提交的报告比较，可以跨阶段比较字数、评分。 |
| BR-21 | 比较对象被删除后，继续向更早报告查找，直到找到有效报告或没有前序报告。 |

### 3.4 一致性

| 编号 | 规则 |
| --- | --- |
| BR-22 | 同一次提交的重复点击、请求重试不能生成多份报告。 |
| BR-23 | 两人同时提交完结报告，后提交者不能静默接替，须看到阶段成果已更新提示并重新确认。 |

## 5. 架构决策与业务不变量

### 5.1 建议架构（ADR-01）

继续采用现有 Next.js Web/API、SQLite、Worker、文件存储，不引入微服务或额外消息中间件。

- API 层：认证、输入校验、错误码、请求幂等协议。
- 应用服务：准备上传、正式提交、撤回、分析入队、洞察入队等用例编排。
- 领域策略：阶段转换、报告角色、操作资格、比较选择，供 API 与 Worker 共享。
- 仓储层：事务、唯一约束、序号分配、成功记录、任务与事件持久化。
- 查询投影：阶段分组、当前成果、最新提交、比较结果、服务端操作能力。

project 是阶段推进的一致性边界；报告单独保存不可变正文与结果历史。无需每次将所有报告加载进内存来执行命令。

### 5.2 不变量

- INV-01：正式报告必有有效阶段，且阶段属于同一课题。
- INV-02：正式报告的阶段、文件内容、阶段版本、课题提交序列不可修改。
- INV-03：阶段内版本唯一，全课题提交序列唯一；失败准备不产生正式版本。
- INV-04：一个课题最多一个进行中阶段；已完成阶段不回退。
- INV-05：一个阶段最多一份当前完结报告；被引用报告存在、有效且属于该阶段。
- INV-06：没有报告的阶段也可以完成；不能从报告数量反推完成状态。
- INV-07：提交确认、完结接替、阶段推进、审计、分析任务持久化在同一事务内完成。
- INV-08：同一次提交最多生成一份正式报告；不同用户的并发完结必须执行冲突确认。
- INV-09：成功历史单调增加，不能因最新任务失败、取消或清理当前缓存而归零。
- INV-10：当前完结报告不可删除；删除更新报告不修改阶段状态。
- INV-11：比较基准严格在目标报告之前、同课题且有效，不得指向自己、后序或其他课题。
- INV-12：课题最新提交不等于当前研究阶段的成果；补交早期阶段不回退研究进度。

## 6. 领域与数据模型

### 6.1 阶段实体（ADR-02）

建议新增关系表 project_stages，将 milestones_json 转换为兼容输出投影，不再作为第二份可写事实来源。

| 字段 | 含义 |
| --- | --- |
| id、project_id | 稳定阶段身份及所属课题 |
| ordinal、title | 课题内阶段顺序、阶段名称 |
| objective、description | 阶段研究任务与说明 |
| planned_start_at、planned_end_at | 计划起止时间，不直接决定状态 |
| lifecycle_status | not_started / in_progress / completed |
| risk_state | 风险提示，独立于 lifecycle_status；逾期不自动完成 |
| started_at、completed_at | 首次实际开始、首次完成时间；补交不覆盖 completed_at |
| completion_reason | report_completion / skipped / migrated，记录首次完成原因 |
| current_completion_report_id | 当前完结报告，可空；跳过无报告阶段允许为空 |
| next_report_version | 阶段内下一个提交版本，删除不回收 |
| state_revision、completion_revision | 生命周期/成果并发控制令牌，仅用于协议 |

课题增加或明确：plan_revision、workflow_revision、next_submission_sequence、completed_at。当前阶段由阶段状态查询得出；如缓存 current_stage_id，必须同事务维护，不能成为独立可写状态。

建议使用唯一索引保证同课题阶段顺序唯一，并使用部分唯一索引保证同课题至多一个 in_progress。更新当前阶段时先关闭原阶段再开启目标，避免瞬时违反约束。

### 6.2 报告提交实体（ADR-03）

建议代码领域名逐步从 ReportVersion 收敛为 ReportSubmission。为降低迁移范围，物理表 report_versions 可暂时保留，不要求一次重命名所有 report_version_id 外键。

| 字段 | 含义 |
| --- | --- |
| id、project_id、stage_id | 正式身份与不可变归属；现有 milestone_id 可在过渡期承担 stage_id 物理字段 |
| stage_version | 阶段内 V 序号，由阶段计数器分配 |
| submission_sequence | 全课题成功提交序号，由课题计数器分配 |
| submitted_as | 提交时选择 update / completion，历史事实不可变 |
| current_role | API 派生字段：是阶段 current_completion_report_id 则 completion，否则 update |
| title、file_name、source_key、file_hash、source_size | 报告与不可变文件元数据 |
| paragraph_count、character_count | 基础解析成功后得到的自身指标 |
| submitted_by、submitted_at | 正式提交人、服务器确认时间，不使用文件时间作为先后依据 |
| was_first_stage_submission | 提交时是否为阶段第一份正式报告，用于稳定的首份比较豁免 |
| first_analysis_succeeded_at | 分析首次成功时间，单调保留 |
| first_insight_succeeded_at | 洞察首次成功时间，独立于分析 |
| current_analysis_id、current_insight_id | 当前有效成功成果引用；历史成功产物另行保留 |
| deleted_at、deleted_by、deletion_reason | 逻辑撤回/删除标记，用于保留序号与审计 |

以阶段 current_completion_report_id 作为当前完结角色的唯一权威来源，避免同时维护多个报告布尔值。一次更新指针即可使旧完结报告在查询投影中成为更新报告；记录明确的接替事件。

数据库约束：

- UNIQUE(stage_id, stage_version)。
- UNIQUE(project_id, submission_sequence)。
- 阶段与报告课题一致，采用复合外键或等价数据库约束保障，不只依赖前端校验。
- 完结指针需保证指向同阶段有效报告；限制删除被引用报告。
- source_key、stage_id、stage_version、submission_sequence 正式提交后由应用与数据库防护禁止改写。
- 旧 version 字段如过渡保留，只作为兼容字段，不得再驱动新 UI 或权限。

**版本与首份策略建议（ADR-04）**：删除不重排、不复用序号；V1 删除后新提交仍是 V2/V3，不重新成为首份。was_first_stage_submission 在提交时固定。此删除后的“首份”解释列入 Q-03，需评审签认。

### 6.3 上传准备记录

新增 report_uploads（或等价暂存实体）：upload_id、project_id、actor_id、临时/最终不可变文件键、hash、解析状态、解析结果、过期时间、正式 report_id。

准备状态：receiving → parsing → ready → committed；失败进入 failed，过期进入 expired。

ready 不等于正式报告：不进入报告库，不分配 V，不参与比较，不推进阶段，不成为最新。

### 6.4 幂等与审计

提交请求表：actor_id、project_id、idempotency_key、request_digest、状态、report_id、可重放响应。唯一键限制同一操作者、课题下的请求身份。

事件至少包括：报告提交、跳阶段、阶段首次完成、完结报告接替、报告撤回、任务入队/成功/失败、并发冲突确认。记录 actor、report/stage/project ID、前后引用、request_id、时间；不得把文件正文、密钥写进普通日志。

## 7. 阶段状态机

### 7.1 建议初始化与计划编辑边界

ADR-05：研究计划至少包含一个阶段；首次启用计划时阶段01进入进行中，其余未开始。空计划课题不能提交报告，界面引导补充计划。

ADR-06：已有正式提交后冻结阶段顺序与删除，允许有审计地修改名称、描述、排期。课题完成后不自动追加新阶段重新打开课题。是否开放未开始阶段的增删重排列入 Q-02，当前设计不偷偷增加回退通道。

### 7.2 转换表

| 目标阶段 | 提交类型 | 前序未完成阶段 | 目标阶段结果 | 后续阶段 |
| --- | --- | --- | --- | --- |
| 当前进行中 | update | 不变 | 进行中 | 不变 |
| 当前进行中 | completion | 不变 | 完成并指定成果 | 第一个后续未开始阶段进入进行中 |
| 后续未开始 | update | 全部标记完成，原因 skipped | 进行中 | 其后保持未开始 |
| 后续未开始 | completion | 全部标记完成，原因 skipped | 完成并指定成果 | 下一阶段进行中；没有下一阶段则课题完成 |
| 已完成 | completion | 不变 | 保持完成，补交或接替成果 | 当前研究阶段不变 |
| 已完成 | update | 不变 | 拒绝 | 不变 |

跳过的前序阶段可能已有更新报告，必须保留，不能为了“无报告跳过”清除旧成果。跳过只结束研究状态，不自动把最近更新报告提为完结报告。

补交 skipped 阶段时可设置成果指针，但保留其首次完成时间、首次完成原因，通过新事件记录补交，不改写历史为“当时有报告完结”。

计划中若存在不合法多进行中/非连续完成状态，命令应返回一致性错误并要求修复，不通过 MAX(version) 或报告数猜测当前阶段。

## 8. 上传确认、事务与故障恢复

### 8.1 推荐两步协议（ADR-07）

用户仍只需一次明确“确认上传”，前端依次完成准备和确认；两步协议是工程边界，不是要求用户重复操作。

1. 校验登录身份、上传权限、文件类型、大小及阶段选择。
2. 上传并基础解析，文件写入受保护的稳定不可变位置，准备记录变为 ready。
3. 发送确认命令，携带 upload_id、stage_id、report_kind、幂等键、计划/流程/成果令牌。
4. 服务端短事务内重新校验身份与权限、归属、准备所有者、阶段状态及并发令牌。
5. 分配阶段版本与课题提交序列，保存正式报告、基础解析指标、首份标记。
6. 按状态机推进阶段、接替成果，维护计数器与 revisions。
7. 保存初次分析任务或可靠待派发事件，写审计和幂等结果，提交事务。
8. 返回正式报告；Worker 异步进行 AI 分析，预算不足或服务故障只影响分析状态。

现有 start/createReportJob 将报告提交与 AI 入队预算耦合的部分必须拆开：AI 配置错误、预算不足不能回滚已满足 BR-03 的正式交付。可创建待分析状态与可靠调度事件，之后按现有预算机制准入。

### 8.2 SQLite 与文件一致性

- 使用 BEGIN IMMEDIATE 或现有等价事务封装串行化同一数据库写入；不在写事务内上传、解析、调用 AI。
- 文件系统操作不能伪装成与 SQLite 原子提交。提交前保证文件已持久化；提交失败文件仍归暂存记录管理，可重试或到期清理。
- 数据库事务失败：不出现正式报告、不改变阶段、不降级旧成果；准备文件保留用于恢复。
- 数据库成功但响应丢失：相同幂等键查询并返回原 report_id，不再分配版本。
- 数据库成功但 Worker 通知失败：Worker 从数据库任务/事件扫描恢复，不能依赖一次内存回调。
- 暂存清理必须确认未被正式报告引用、未在确认事务中使用；不能按文件年龄直接删除。

### 8.3 幂等规则

先查已成功请求，再校验可能已经过期的成果令牌，保证响应丢失后的重试能获得原成功结果；仍需验证操作者对该请求的访问权。

- 同键同请求：返回同一结果或处理中状态。
- 同键不同文件、阶段或类型：409 IDEMPOTENCY_KEY_REUSED。
- 同一 upload_id 不能通过换幂等键生成第二份正式报告。
- 冲突后没有提交报告；用户重新确认时使用新的命令幂等键和最新令牌，复用仍有效的准备文件。
- 同内容的两次独立提交不等于同一次请求；是否允许同 hash 再提交列入 Q-04，不拿文件 hash 代替幂等键。

## 9. 并发控制

### 9.1 完结报告接替

确认请求携带 expected_completion_revision 和 expected_completion_report_id，均在事务内比较，包括首次成果指针为空的情况。

发现变化时返回 409 STAGE_COMPLETION_CHANGED，包含最新成果的安全摘要及新令牌，界面提示“阶段成果已更新，请确认是否继续补交”。用户不能用客户端 force=true 绕过比较；重新确认后如果再次变化，仍须再次冲突。

### 9.2 阶段推进冲突

涉及跳阶段或当前阶段完结时，检查 plan_revision、workflow_revision。有人在准备期间推进了阶段，必须重新计算影响并提示，不可把原来的 update 静默转成 completion。

- 两份当前阶段 update：可以依次成功，分配不同序号，不因为仅新增报告而强制弹阶段冲突。
- update 与 completion 并发：update 先成功则 completion 可随后完成；completion 先成功则旧 update 请求拒绝，用户须确认补交完结类型。
- 两份 completion：第一份成功，第二份成果令牌冲突。
- 不同阶段的跳阶段命令：通过 workflow_revision 检测，后者重新确认范围。
- 非推进性的早期阶段补交检查该阶段成果令牌，不无谓回退或切换当前阶段。

revision 是内部乐观锁，不作为用户可见的报告 V 编号。

## 10. 分析与洞察策略

### 10.1 共享资格判定

对 analysis、insight 分别执行：

允许请求 = 已授权 ∧ 报告有效且已正式提交 ∧（报告为全课题最新有效提交 ∨ 该操作从未成功）。

有同类型活动任务时复用/返回活动任务，不再重复入队。预算、频率、内容有效性等既有保护继续生效，不因业务资格满足而绕过。

同一个公共策略必须应用于：分析 POST、任务重试、洞察 POST、Worker 恢复、前端能力字段；移除“非最大旧 version 一律拒绝”的独立判断。

### 10.2 成功与结果保留

- 首次成功定义为产物通过现有质量校验并正式持久化/发布，不是仅模型请求返回或任务开始。
- 成功标记、成功产物引用、任务成功状态同事务提交；失败/取消不设置成功标记。
- 已成功最新报告再次分析失败，保留之前成功结果和成功历史；之后变旧仍禁止手动重跑。
- 分析成功不等于洞察成功；旧报告分析成功、洞察从未成功时，仍允许首次生成洞察。
- 删除缓存、改变 UI 当前快照不得抹掉“曾成功一次”的事实。
- 洞察重复生成也应保留历史成果，不只原地覆盖当前洞察行；现有次数/预算限制需与新策略共同判断。
- 任务绑定明确的 report_id、分析代次及冻结评价上下文；完成旧报告的任务只能发布到该报告，不能改变课题最新提交或阶段成果指针。迟到回调通过任务代次/发布令牌校验，不能覆盖同报告更新代次的有效成果。
- 同一报告、同一操作至多一个活动任务；重试复用活动任务，成功历史与结果引用更新使用事务，避免两个“首次尝试”同时成功后相互覆盖。

BR-17 明确保障首次任务继续完成。对“作为最新合法入队的再次分析，在执行前变旧”的任务，ADR-08 建议按入队时授权继续完成，不由新提交中断；这是额外工程建议，列入 Q-05。Worker 仍必须拒绝给已撤回报告重新发布结果。

### 10.3 删除与活动任务

ADR-09：更新报告存在活动分析/洞察时，先返回 409 REPORT_PROCESSING；允许负责人取消，任务终态后再删除。不要边删除边允许 Worker 复活报告。若未来采用取消后立即软删除，需要发布端 fencing token，本期不同时支持两套策略。

## 11. 动态比较设计

### 11.1 基准选择

输入当前有效报告 R：

1. R.was_first_stage_submission 为真：返回 no_comparison，原因 first_stage_submission。
2. 在同 project_id 内查找 submission_sequence 小于 R 的最大序列，排除 deleted/withdrawn、未正式提交记录。
3. 找不到：返回 no_predecessor。
4. 找到 B：返回 B 的 ID、阶段名、阶段版本、提交时间及可比较指标。

使用序列查询等价于删除后沿前序链不断回溯，但不依赖容易断裂的 previousVersionId。不要使用时间字符串单独决定顺序，也不要把仍存在但尚未分析成功的 B 跳过去找“更好看”的评分。

### 11.2 指标与快照分离

- 字数变化 = R.character_count - B.character_count。
- 评分变化 = R 当前有效成功评分 - B 当前有效成功评分；任一不可用则评分变化 unavailable，不使用 0 代替。
- 基准取当前有效成功成果：最新报告合法重分析后，相关比较读取新的成功结果，但旧分析自身保持不变。
- 跨阶段评分可比较，UI 标注双方阶段与基准报告；不同阶段评价上下文不同，差值仅为参考，不直接解释为同口径质量提升。
- 原始分析快照不再承担可变 previousOverall；API 用独立 comparison 对象返回。
- 缓存需随报告删除、成功产物更新、基准报告标签变更失效；不能仅刷新被删除报告自己的页面。

建议 comparison 输出：status、reason、baselineReportId、baselineLabel、characterDelta、scoreDelta、baselineAnalysisId、currentAnalysisId。无对比与零变化必须是不同状态。

### 11.3 示例

| 全课题提交序列 | 阶段内标识 | 行为 | 比较结果 |
| --- | --- | --- | --- |
| 1 | 阶段01 V1 | 更新 | 阶段首份，不展示 |
| 2 | 阶段01 V2 | 完结 | 与序列1比较 |
| 3 | 阶段02 V1 | 更新 | 阶段首份，不展示，虽然存在序列2 |
| 4 | 阶段01 V3 | 补交完结，V2降为更新 | 与序列3比较，跨阶段；阶段02仍进行中 |

若删除序列3，则序列4改与序列2比较。若之后删除已降级的序列2，则序列4改与序列1比较。无前序时停止展示变化，不要求重新运行序列4的 AI。

## 12. 权限、撤回与安全

上传/完结权限已经确认：管理员或当前课题负责人。后端应新增明确能力 canSubmitReport，不再复用包含 editor 的宽泛 canManage。

其他写操作的角色边界尚未逐项确认。ADR-10 建议本期报告删除、分析/洞察触发也仅限负责人/管理员；列入 Q-01，不将建议冒充业务已确认规则。读取范围沿用现有访问策略，另行评审，不借本次阶段改造扩大或缩小读权限。

删除更新报告时：

1. 在事务内重验权限、当前完结引用、活动任务状态。
2. 写删除标记与审计，不删除或重排版本/提交序列。
3. 不重建阶段状态，不撤销课题完成。
4. 若删除的是全课题最新有效报告，按剩余提交重新解析最新；相应操作资格随之更新。
5. 比较读取自动排除此报告，必要时失效缓存。
6. UI/API 不再读取已删除正文及结果；物理文件保留期限、备份与清理策略另行明确。

撤回与删除建议本期使用相同不可见状态，保留动作原因；不开放恢复入口以免引入新的基准与最新变动规则。是否恢复及物理保留期限列入 Q-06。

安全要求：准备文件只能被所属用户在授权课题中提交；不得信任客户端 source_path、project_id 派生归属或角色字段；权限在确认事务中重新校验，负责人变更/账号停用后不能用旧准备请求越权提交。

## 13. API 设计建议

接口路径为建议契约，实施时可兼容现有 URL，但语义与错误码应统一。

| 方法与路径 | 用途/变化 |
| --- | --- |
| POST /api/projects/:projectId/report-uploads | 接收文件、解析，创建准备记录；不创建正式报告 |
| GET /api/projects/:projectId/report-uploads/:uploadId | 查询解析状态、错误、是否已提交及 reportId |
| POST /api/projects/:projectId/reports | 确认提交准备记录；携带幂等键、stageId、reportKind、并发令牌 |
| GET /api/projects/:projectId/stages | 阶段计划、状态、当前成果、报告计数及 revisions |
| GET /api/projects/:projectId/stages/:stageId/reports | 阶段内 stageVersion 倒序、稳定分页 |
| GET /api/projects/:projectId/reports/history | 阶段分组与可选提交时间线，不再默认 entries[0] 同时代表所有 current |
| GET /api/reports/:reportId | 报告、所属阶段、currentRole、比较对象、分析/洞察状态与 capabilities |
| DELETE /api/reports/:reportId | 逻辑撤回/删除更新报告；拒绝当前完结报告 |
| POST /api/reports/:reportId/analyze | 使用新的共享资格策略，允许旧报告首次分析/失败重试 |
| POST /api/reports/:reportId/insight | 独立判断洞察成功历史，使用相同新旧规则 |
| 原修改归属 PATCH、覆盖源文件 PUT | 下线；显式返回 REPORT_STAGE_IMMUTABLE / REPORT_SOURCE_IMMUTABLE，不提供隐藏兼容旁路 |

确认请求包含：uploadId、stageId、reportKind、expectedPlanRevision、expectedWorkflowRevision、expectedCompletionRevision、expectedCompletionReportId。按操作类型只校验相关令牌，避免无关补交冲突。

查询契约显式区分：currentStage、stageLatestReport、stageCompletionReport、latestSubmissionReport、selectedReport。分页不能改变当前阶段或最新报告判断，最新查询不得只依赖当前页第一行。

capabilities 建议返回：canSubmitUpdate、canSubmitCompletion、canDelete、analysisAction（start/retry/rerun/view/none）、insightAction、disabledReason。前端展示能力不替代服务端校验。

### 13.1 错误语义

| 状态码 | 示例错误码 | 含义 |
| --- | --- | --- |
| 400 | INVALID_REPORT_KIND / IDEMPOTENCY_KEY_REQUIRED | 输入缺失或格式错误 |
| 401 / 403 | UNAUTHENTICATED / REPORT_SUBMIT_FORBIDDEN | 未登录或无权限 |
| 404 | REPORT_NOT_FOUND / STAGE_NOT_FOUND | 资源不存在或按既有访问策略不可见 |
| 409 | STAGE_COMPLETION_CHANGED / PROJECT_WORKFLOW_CHANGED | 用户需重新确认成果或推进范围 |
| 409 | STAGE_ALREADY_COMPLETED / COMPLETION_REPORT_PROTECTED | 不满足更新/删除规则 |
| 409 | HISTORICAL_OPERATION_ALREADY_SUCCEEDED | 旧报告相应操作已成功过，不能重跑 |
| 409 | REPORT_PROCESSING / IDEMPOTENCY_KEY_REUSED | 活动任务或重复键冲突 |
| 409 | REPORT_STAGE_IMMUTABLE / REPORT_SOURCE_IMMUTABLE | 正式报告归属、文件不可改 |
| 413 / 415 / 422 | FILE_TOO_LARGE / FILE_TYPE_UNSUPPORTED / REPORT_PARSE_FAILED | 文件或基础解析问题 |

业务拒绝不能统一作为 500 返回，尤其要修复现有历史报告分析拒绝被映射为服务器错误的问题。

## 14. 前端交互与展示

### 14.1 上传入口

- 负责人/管理员可见，其他用户没有入口且不能调用 API。
- 文件 → 阶段 → 类型 → 影响确认 → 上传解析 → 正式提交结果。
- 已完成阶段只显示“补交/更新完结报告”；不提供普通更新选择。
- 选择后续阶段时，确认区列出将自动完成的阶段，说明已有报告不会删除。
- 已有完结报告时，展示即将接替的报告；提交期间成果发生变化时必须再次确认。
- 准备失败可重试或取消，不能在历史页面制造一份看似正式的失败报告。

### 14.2 课题详情与报告库

- 阶段按计划 ordinal 展示，不按最近上传时间改变研究顺序。
- 阶段内报告按 stage_version 倒序，可突出当前完结报告。
- 跳过无报告阶段显示“已完成 · 跳过，暂无报告”，提供授权后的补交入口。
- 阶段徽标统一“阶段01 · 名称”，报告标识统一“阶段名 Vn”，完结成果另加“完结报告”。
- 总览“报告版本总数”改为明确的“已提交报告数”，单位为份；阶段完成数量独立统计，不拿报告数量替代。
- 报告原文、洞察空状态、通知、操作提示、aria-label、下载信息使用同一标签生成逻辑。

### 14.3 默认选择建议（ADR-11）

- 课题首页默认展示当前研究阶段，不因早期阶段补交跳回旧阶段。
- 当前阶段有报告时默认最新阶段内提交；暂无报告时展示阶段任务和上传入口，不伪装成上一阶段。
- 已完成阶段默认当前完结报告；跳过且无成果时显示空状态。
- 课题全部完成默认最后阶段完结报告。
- 全课题最新报告作为独立“最近提交”入口，操作能力仍按全课题提交顺序判断。

默认页面可以展示一份“旧提交但仍为当前阶段成果”的报告，其重新分析按钮可能不可用；应解释原因，不能为让按钮可用而改变研究阶段。

## 15. 存量数据迁移与兼容

### 15.1 迁移原则

当前 lib/db/migrate.ts 明确包含破坏性 schema 重置指导及 checksum 校验。**本报告不授权删除 storage，也不能假定现有迁移器已经支持安全升级到新模型。** 实施前选择并验证升级路径。

建议默认按保留数据设计：离线备份、迁移演练、完整校验、切换、可恢复回滚。只有用户明确接受丢弃数据时，才另行执行全新初始化。

### 15.2 映射方案

| 存量数据 | 目标处理 |
| --- | --- |
| milestones_json | 保留原阶段 ID，抽取到 project_stages；空计划、多进行中等异常输出清单 |
| ReportVersion.id 与各分析外键 | 尽量保持不变，避免破坏文件、任务、快照、洞察关联 |
| 全局 version | 作为旧提交顺序证据，转换为 submission_sequence，不再作为阶段内显示版本 |
| 同阶段旧报告 | 按确定的旧提交顺序分配 stage_version；迁移后删除不复用 |
| stage/final | 不能机械映射成 update/completion；旧 stage 本来也会完成阶段，必须结合阶段状态和报告记录判断 |
| 多份旧“完结”候选 | 为每阶段生成推荐当前成果及接替历史；存在歧义时由负责人确认，不静默覆盖 |
| 已完成但没有报告 | 保留完成，completion_reason=migrated；无证据时不能伪造为用户主动跳过 |
| 未关联或关联失效报告 | 不自动按 version 猜阶段；切换前人工归档关联或隔离为只读 legacy_unassigned |
| uploaded/failed 解析记录 | 不冒充新模型成功提交；单列迁移异常/历史失败记录，决定重解析或隔离 |
| 历史分析、洞察 | 保留成功产物；由可信成功任务/快照回填首次成功标记 |
| previousVersionId、previousCharacterCount、previousOverall | 保留必要旧快照审计，但新读取不再把它们当比较权威来源 |

存量源文件曾被覆盖、阶段归属曾修改的历史，可能无法仅凭当前数据重建。迁移报告必须标明“不完整历史”，不得伪造旧文件与事件。

### 15.3 推荐迁移步骤

1. 只读盘点：阶段、报告、孤立文件、活动任务、成功产物、hash 冲突、归属异常。
2. 停止写入口并处理/暂停 Worker 活动任务；制作数据库一致性备份与文件清单备份，考虑 SQLite WAL。
3. 在副本运行转换：创建新结构、回填序号、成果引用与成功历史，输出需人工确认清单。
4. 校验引用、唯一性、阶段状态、报告/成果数量及文件 hash；解决异常后才允许切换。
5. 修改或扩展迁移策略和 schema-contract，使校验账本合法；不得修改已应用迁移 checksum 来绕过验证。
6. Web、Worker、数据库作为同一发布单元切换，不混跑新旧提交规则；先启只读验收，再启写入。
7. 观察提交、比较、任务成功率；保留回滚窗口与操作审计。

回滚：切换尚未开放写入时可恢复备份；开放写入后不能简单降级二进制，否则会丢失/误读新提交。必须冻结写入并导出或重放新增数据后执行经过演练的恢复流程。备份恢复不能覆盖新文件而不留清单。

UNIQUE(project_id, file_hash) 现有限制与“相同正文从更新变为完结”“相同文件跨阶段提交”可能冲突。Q-04 确认后决定移除此业务唯一约束，文件物理去重与报告提交身份分开。

## 17. 测试与验收矩阵

| 用例 | 操作 | 验收结果 |
| --- | --- | --- |
| AT-01 | 同阶段连续上传两份 update | V1/V2 同阶段，仍进行中，旧文件保留 |
| AT-02 | 当前阶段上传 completion | 指定成果，当前完成，下一阶段进行中 |
| AT-03 | 阶段01进行中直接向阶段03传 update | 前两阶段完成，原报告保留，阶段03唯一进行中 |
| AT-04 | 直接向最后阶段传 completion | 前序完成，课题完成，无进行中阶段 |
| AT-05 | 已完成阶段传 update | 拒绝，不生成正式报告，不消耗正式版本 |
| AT-06 | 已完成阶段补交 completion | 旧成果降级，新成果接替，后续当前阶段与完成时间不变 |
| AT-07 | 跳过无报告阶段补交首份 completion | 生成该阶段 V1，保持阶段/课题状态，不显示比较 |
| AT-08 | 解析失败或文件保存失败 | 无正式报告、无阶段变化、旧成果不降级 |
| AT-09 | AI 分析失败/预算不足 | 报告与阶段提交保持成功，显示可恢复分析状态 |
| AT-10 | 相同提交重复点击、网络超时重试 | 同 reportId，仅一条正式报告与一组状态事件 |
| AT-11 | 同键不同参数、同 uploadId 换键 | 拒绝或返回既有结果，不制造第二份 |
| AT-12 | 两人同时提交 completion | 一方成功，另一方409；确认后才能接替 |
| AT-13 | 并发 update/completion、跨阶段跳转 | 按事务及令牌规则处理，无多进行中、无静默改类型 |
| AT-14 | 编辑/旁观者绕过 UI 上传、准备后被撤权 | 403；无正式写入 |
| AT-15 | 任意正式报告 PATCH 改归属或 PUT 覆盖源 | 拒绝，文件与归属不变 |
| AT-16 | 删除当前 completion | 拒绝；先被接替后才按 update 策略处理 |
| AT-17 | 删除旧 update | 阶段不回退，版本不重排，比较基准动态回溯 |
| AT-18 | 删除最新 update | 最新资格转移至剩余最大提交序列，不改变当前阶段 |
| AT-19 | 最新报告重新分析/洞察 | 角色、预算满足时允许，保留历史成功结果 |
| AT-20 | 旧报告已成功的操作再次请求 | 409；API、重试入口、UI一致 |
| AT-21 | 旧报告首次失败后重试 | 允许；成功后关闭该操作手动重跑资格 |
| AT-22 | 首次任务执行中有新报告提交 | 首次任务继续完成，不因新旧变化取消 |
| AT-23 | 旧报告分析成功但洞察未成功 | 分析禁止重跑，洞察允许首次/失败重试 |
| AT-24 | 最新报告曾成功后重跑失败，再变旧 | 曾成功标记保留，不能伪装首次重试 |
| AT-25 | 阶段首份但课题已有其他报告 | 不显示字数/评分变化，非虚假“0变化” |
| AT-26 | 非首份跨阶段前序比较 | 基准为提交时序前一有效报告，不是前一阶段成果 |
| AT-27 | 比较对象连续删除直到无前序 | 自动回溯；最终不比较；无需重新分析当前报告 |
| AT-28 | 基准评分未成功但字数可用 | 字数可比较，评分 unavailable，不跳过基准或当零 |
| AT-29 | 阶段首份删除后再提交 | 按Q-03签认策略执行，版本不复用 |
| AT-30 | 补交早期阶段成为全课题最新 | 首页不回退研究阶段，分析资格按全局提交判断 |
| AT-31 | 长阶段名、阶段数>12、V>99 | 标签有完整提示，不依赖固定中文数组，不截错身份 |
| AT-32 | DB提交后响应丢失/进程退出 | 重放同一提交；任务从数据库恢复 |
| AT-33 | 暂存清理与确认/活动任务并发 | 不误删正式文件，不复活已删除报告 |
| AT-34 | 历史迁移异常、多成果、无阶段 | 输出异常并阻止静默错误映射，数据可追溯 |
| AT-35 | 对同一角色从不同分析/洞察/重试入口操作 | 资格与错误码一致，无历史替换旁路 |

## 18. 可观测性与完成标准

建议记录并监控：准备/解析失败率、正式提交成功率、幂等重放次数、成果/阶段冲突次数、孤立文件数量、待调度任务延迟、旧报告非法重跑拒绝、阶段不变量异常、比较基准缺失原因。

发布完成标准：

- BR-01至BR-23均有可执行验收覆盖。
- API与Worker不再依赖旧全局version判断阶段或简单拒绝所有旧报告。
- 不存在改归属、原地替换源文件的隐藏写入口。
- 所有用户可见V编号均为阶段内版本，当前阶段与最近提交明确区分。
- 上传失败不推进阶段，并发接替无静默覆盖。
- 首份、跨阶段比较、连续删除回溯行为符合约定。
- 迁移报告、异常处理、备份恢复与发布联动均已演练；不得宣称仅单测通过即完成上线。

## 19. 待签认边界与建议默认值

以下不推翻已确认主规则，但实施前需要明确，以免工程人员自行补充产品行为。

| 编号 | 待确认事项 | 建议默认值 |
| --- | --- | --- |
| Q-01 | 删除、分析/洞察触发的角色是否也仅负责人/管理员 | 统一限负责人/管理员 |
| Q-02 | 初始阶段启用、已有报告后增删/重排计划 | 启用计划后首阶段进行中；已有提交冻结顺序与删除；名称和排期可审计修改 |
| Q-03 | 首份删除后是否重新产生“阶段首份”；版本是否复用 | 首份按首次正式提交历史固定；删除不重置、不复用V序号 |
| Q-04 | 相同文件从更新再提交为完结，或跨阶段提交 | 允许不同明确提交，提醒重复；幂等只去重同一次请求，文件存储可去重 |
| Q-05 | 合法入队的再次分析/洞察执行中报告变旧 | 入队时授权有效则继续完成；首次任务继续完成已明确确认 |
| Q-06 | 撤回与删除差异、恢复能力、文件保留期限、活动任务删除 | 本期统一逻辑删除且不恢复；活动任务先取消至终态；保留期限需运营/安全签认 |
| Q-07 | 既有洞察再生成次数限制与新“最新可重跑”规则 | 新规则决定资格，既有预算/次数保护暂保留；如产品要求无限次须另行修改 |
| Q-08 | 存量不完整阶段归属与旧成果如何迁移 | 默认保留数据、人工确认歧义；禁止自动按旧V号猜阶段，禁止未经授权清库 |

这些建议可作为实现默认方案提交审批，但不应在代码中悄悄生效。特别是数据迁移方式、文件保留和删除角色需要明确签认。

## 20. 结论

目标系统应以阶段状态机管理进度，以阶段成果指针管理完结报告，以阶段内版本管理展示，以全课题成功提交序列管理新旧与比较。四者独立建模、在必要的短事务内协调。

本报告为设计交付物，未修改业务代码、未迁移数据库、未部署服务。下一步是签认第19节边界并按P0—P5逐步实施，不再通过局部替换“V1/V2”文案代替领域改造。
