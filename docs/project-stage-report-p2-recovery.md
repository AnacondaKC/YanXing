# P2 项目写入与准备文件恢复

## 1. 交付与运行边界

本轮完成项目创建/计划编辑和准备文件恢复的后端机制，继续使用新项目模型，不做存量迁移、回填或双模型兼容。

入口是 lib/reports/submission-runtime.ts 的显式组合：
- repository.createProject：创建课题、负责人/协作者、阶段及初始进度，审计与业务数据同事务。
- repository.editPlan：expectedPlanRevision 乐观锁、计划冻结、排期/描述更新、前后快照审计。
- projects.create / projects.editPlan / projects.plan：注入式 HTTP 处理器，宿主提供可信会话身份，保留现有 CSRF/来源校验。
- recovery.runBatch(limit)：内部维护入口，领取并回收过期/失败的准备记录。
- recovery.reconcileQuota()：只修复数据库账目，不删除文件或修改报告正文。

这些入口已组合并联测，但不自动注册 app/api 路由、不启动维护守护进程，也不修改当前业务数据库。P3 Worker 和 P4 页面切换时一起挂接，不能据此宣称旧旁路已关闭。

## 2. 项目与阶段事务

- 活跃研究人员可以为自己创建课题；管理员可以指定其他活跃用户作为负责人。
- 成员必须存在且活跃；负责人不能同时是协作者；协作者数量沿用现有限制。
- 标题、目标、背景及阶段结构经过严格契约和领域校验；不接受旧 milestones 或客户端进度字段。
- 新项目只有一个初始进行中阶段。阶段表是权威计划，不向旧 milestones_json 双写。
- 无正式提交时可以增删/重排阶段，按新计划重新初始化阶段；准备文件只属于课题，不因此被删除。
- 任意一次正式提交之后，阶段身份、数量、顺序被冻结，逻辑删除全部报告也不能解除冻结。
- 仅修改名称、说明、排期时保留开始/完成时间、完结报告指针和版本计数。
- 每次编辑递增 planRevision 并更新课题更新时间；旧确认令牌随后必须重新获取。审计失败会回滚整次写入。

## 3. 回收与确认如何互斥

准备记录增加 reclaiming / reclaimed 状态、恢复租约令牌、租约截止时间、重试时间、诊断码和回收完成时间。

1. 在 BEGIN IMMEDIATE 内选择失败或已过期记录。已经 committed、已有正式报告文件引用的记录不能领取。
2. 原子转为 reclaiming 并取得租约。确认事务只能提交 ready，故不能与回收同时取得处置权。
3. 在数据库事务外删除已知、受管的准备文件及临时文件。
4. 删除和目录持久化完成后，在另一短事务内检查租约并原子释放配额、标记 reclaimed。
5. 删除失败保持配额，延迟重试。进程退出后，其他恢复者可在租约过期后接管；旧令牌不能确认完成或释放配额。
6. 数据库失败发生在文件删除之后时，配额释放会回滚；下次幂等清理不存在的文件后再完成账目。

reclaimed 保留身份记录，不能重新启用，也不能复用上传ID。

### 正在运行的旧上传进程

仅在重命名前检查一个状态是不够的：检查之后暂停的进程仍可能在回收结束后写回文件。

生产组合中的 P2 文件写入使用数据库 mutation fence：创建临时文件、每个至多64KiB的写块、创建成果目录以及最终重命名/同步，均先在短写事务中确认记录仍为 receiving/parsing 且未过期。受管写描述符不会跨越网络等待；读流、解析与AI不在数据库写事务内执行。

回收一旦取得状态，暂停的旧写入即使恢复、系统时钟回退，也不能重新创建或追加文件。解析完成后还必须经过 markReady 的状态与权限复核。不要绕过 runtime 组合，把未带 fence 的底层文件工具用于可回收的业务上传。

## 4. 物理文件与配额

- 只删除精确归属于该上传ID的文件：ID/ID.docx、ID/ID.pdf，以及 .tmp 中 ID-UUID.upload。
- 不递归删除目录；遇到未知同目录文件、符号链接或路径不安全时停止，保留证据和配额。
- 存储根目录与新数据库绑定。配置不匹配拒绝处置；存储离线不等同于文件已删除。
- 准备文件的配额保留到正式提交或成功物理回收。上传TTL仍由准备记录控制，通用预留过期器不得提前释放仍有持久文件的预留。
- 对账根据准备/报告权威元数据修复预留与正式分配，再从公共分配和预留账本重算全局/用户/课题计数。知识库账目也参与计算，不能被报告账目覆盖。
- 已完成失败清理的 failed 记录保持已释放预留；若恢复流程再次领取，需要恢复必要的保留后再处置。
- 正式报告即使逻辑删除，也保留文件和存储分配。本期没有自动物理删除正式文件的操作。

只读审计会报告不可用/损坏的正式来源、解析正文缺失、准备文件异常、未登记文件、回收后重现文件、分配缺失和计数不一致。正式文件损坏不自动重写，未知文件不自动认领或删除，需人工恢复或核查。

## 5. 恢复命令

必须显式指定已存在的新结构数据库及其私有存储目录；不创建数据库，不安装schema，不迁移数据。以下路径仅为示例，不是当前运行目录。

只读预览（默认不修改文件和数据库）：

~~~bash
node --import tsx scripts/recover-report-uploads.ts \
  --database /srv/yanxing-new/storage/yanxing.sqlite \
  --storage-root /srv/yanxing-new/storage/submissions
~~~

输出 recoveryCandidates 与 issues。确认配置后显式执行有界恢复：

~~~bash
node --import tsx scripts/recover-report-uploads.ts \
  --database /srv/yanxing-new/storage/yanxing.sqlite \
  --storage-root /srv/yanxing-new/storage/submissions \
  --apply --limit 100
~~~

- 每批默认100条，范围1—1000；有更多候选时重复执行。
- 清理失败默认等待60秒重试，租约为60秒；每次重新领取使用不同令牌。
- apply模式：无阻塞/诊断时退出0；仍需处理的阻塞或诊断退出2；参数、根目录绑定或执行错误退出1。
- 命令是受信任的运维工具，不可直接暴露为用户可调用的无鉴权HTTP接口。
- 将来由维护进程周期调用同一入口；本轮没有启动此进程，也没有在当前业务库上执行apply。

## 6. 验证范围

自动测试覆盖创建及计划审计回滚、跨连接计划冲突、提交后冻结、过期准备回收、缺少source_key的落盘残留、租约失效、连接重启后恢复、清理后数据库失败、暂停的实际流式写入和解析晚到、错误根目录/离线存储、符号链接、未知文件、配额损坏与知识库计数保留、CLI只读预览与重复执行。

这些验证不是物理断电实验、真实机器宕机演练或上线验收；正式部署仍需新库联调、维护任务挂接和P5演练。
